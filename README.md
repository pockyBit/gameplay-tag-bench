# GameplayTag 层级关系存储：五种方案实测对比

针对 [CycloneGames.GameplayTags](https://github.com/MaiKuraki/UnityStarter/tree/main/UnityStarter/Assets/ThirdParty/CycloneGames/CycloneGames.GameplayTags) 的 CSR 平铺结构，用同一棵标签树对比五种 tag 层级存储方案的实测性能。

## 结论

| 操作 | 位段码 | 嵌套集 | 父指针 | CSR 平铺 | 字符串 Span |
| --- | --- | --- | --- | --- | --- |
| `IsAncestor`（4 层） | **0.86 ns** | 3.14 | 5.54 | 7.28 | 8.55 |
| `IsAncestor`（10 层） | **1.28 ns** | 2.85 | 11.43 | 17.74 | 9.81 |
| `MatchesTagDepth`（10 层） | **1.98 ns** | 不支持 | — | 11.56 | — |
| 额外内存/tag | 4 B / 8 B | 8 B | 5 B | 19.4 B / 39.5 B | 0 |

- **纯判定场景，位段码（path code）完胜**：判父子是 CSR 的 8.5~13.9 倍快，且树变深几乎不掉速。
- **CSR 平铺的价值在工程属性，不在性能**：无容量上限、不可变快照单次 `Volatile.Write` 发布、读侧无锁。只在「深树 + 批量取链」一个组合里拿到第一（领先 5%）。
- **嵌套集（DFS 时间戳）被低估**：8 B/tag 做到 O(1) 判父子，无容量天花板；代价是插入要重编号、做不了前缀深度比较。

## 五种方案

| 方案 | 每 tag 存储 | 判父子 | 求父/层 | 跨端自描述 |
| --- | --- | --- | --- | --- |
| 字符串拼接 | 0 | O(len) + 分配 | 切串 | 是（传名字） |
| 位段码 7/7/9/9 | 4 B | O(1) 无分支 | O(1) | 是 |
| 父指针 | 4~8 B | O(深度) 爬 | O(1) | 否 |
| 嵌套集（DFS 时间戳） | 12 B | O(1) 两比较 | O(1) | 否 |
| CSR 平铺 | 4 B + 4×Σ深度 | O(log 深度) | O(1) | 否 |

## 运行

```bash
dotnet run -c Release
```

需要 .NET 10。两棵树用固定种子生成（`20261102` / `20261103`），数字可复现。

标定方式：20 万对查询 × 20 轮取最小值；六种实现全部接受 tag 索引而非字符串，字符串方案只负责比较名字。开跑前会逐对校验六种实现结果一致——**不校验就跑基准等于在测错误的代码**，`tzcnt` 那个 bug 就是靠校验抓出来的。

## 结构

- `Program.cs` — 标签树生成、六种实现、三个操作的基准
- `TagBench.csproj` — 工程文件
- `gameplay-tag-storage-notes.md` — 完整分析笔记（结构讲解、实测数据、踩坑记录、选型结论）
- `gameplay-tag-storage-notes.html` — 同一份笔记的可视化版本，带内联 SVG 图表

## 数据局限

微基准跑的是纯函数，数据全在缓存里。真实游戏里查询夹杂在属性计算中间，缓存状态完全不同——**绝对值别当真，比例可以参考**。多次运行抖动约 ±10%。
