01先看被比较的东西长什么样

分析对象 MaiKuraki/UnityStarter 项目里的第三方库 CycloneGames.GameplayTags
  • 库根目录 · CycloneGames.GameplayTags
  • 本文起点 · Core/TagDataSnapshot.cs
  • 层级构建与判定 · Core/GameplayTagManager.cs（BuildHierarchy / IsAncestorOf）
  • 注册与名字排序 · Core/GameplayTagRegistrationContext.cs

CycloneGames 这套实现没走「每个 tag 挂一个 parent 指针」的老路，而是把每个 tag 的完整祖先链抄一遍，首尾相接铺成一条大数组，再用一张前缀和表当目录。这就是 CSR（压缩稀疏行）。

两个数组的语义完全错位，是理解它的唯一门槛：HierarchyOffsets 是页码，HierarchyPool 是正文。页码里不含任何 tag，正文里才是 tag 编号。

三个位置读法，全部围绕「段尾」展开：

int start = HierarchyOffsets[i];
int end   = HierarchyOffsets[i + 1];   // 同时是 i+1 那段的起点

int root = HierarchyPool[start];          // 段首 = 根
int self = HierarchyPool[end - 1];        // 段尾 = 自己
int dad  = HierarchyPool[end - 2];        // 段尾前一格 = 父（段长≥2 才成立）
int level = end - start;                  // 层级是减法副产品，不单独存
注释里的 -2 是个陷阱

段长 1（根节点）时 end - 2 会跨到上一段的末尾，返回一个完全无关的 tag，不抛异常、不越界，只是给错答案。真实代码里从不用它，而是用 ParentIndices 或区间长度保护。差一错误在这种平铺结构里是隐形的。

04四个反直觉的发现

① 深树上，CSR 比最土的父指针爬升还慢一倍

17.74 对 11.43，而它的内存是父指针的 8 倍。原因：CSR 的成本等于「扫一条长度约等于深度的连续切片」，父指针的成本等于「跳约等于深度的几次指针」。深度 3~4 时连续内存的局部性压得住跳转开销；深度到 9 以后，线性扫描的循环次数上去了，二分的 4~5 次随机访问又打不过顺序数组的几次 L1 命中。两边都不占便宜，只剩内存劣势。

② 批量化并不能普遍加速

CSR 只在「深树 + 批量」这一格拿到第一（11.15），领先 5%。而在浅树上，CSR 批量 6.13 反而比单条 6.94 略快有限，位段码批量 7.49 比单条 7.81 还慢。因为批量能摊薄的只有函数调用和边界校验那 1 ns，真正的成本是往输出缓冲区写 N 个元素，这个成本与批量无关。更有害的是批量版多了个持续累加的写游标 w++，形成依赖链——每条链只有 1~2 个元素时，批量化是负优化。

③ MatchesTagDepth 才是真正的分水岭

浅树 1.82 vs 6.49，深树 1.98 vs 11.56，拉大到 5.8 倍。看循环结构就明白：

// CSR：每次迭代依赖上一次的结果，形成串行依赖链
while (d < shared && _pool[sa + d] == _pool[sb + d]) d++;

// 位段码：一次异或 + lzcnt + 查表，整条指令流完全独立
ulong xor = _ids[a] ^ _ids[b];
return _layout.FirstDiffLevel(xor) - 1;

这不是「把循环写得更快」，是结构上消灭了循环。有意思的是 MatchesTagDepth 正是这个库注释里主推的功能之一，结果它在这个功能上是所有实现里最慢的。

④ 取祖先链的差距小到没有意义

三个实现全落在 6~13 ns 区间。反推成本模型：浅树 6.94 ns / 1.88 个元素、深树 12.21 ns / 5.66 个元素，得到每元素约 1.5 ns、固定开销约 4.4 ns。取出的元素只有个位数时，一次函数调用、参数校验、循环建立、缓冲区写入这些固定开销占了总成本六成以上，存储布局的差异被完全淹没。这也解释了为什么 IsAncestor 能拉开差距——它不写任何缓冲区，输出只有一个 bool，剩下的全是纯计算。

05踩坑记录：位段码判层级必须用 tzcnt

第一版用 LeadingZeroCount 判层级，结果 10 万对真祖先全部判错。因为位段从低位向高位是「浅 → 深」，最高置位永远落在最浅那一层（L1 的 1 就是 bit54，任何后代都带着它）。要找最深一级必须用 TrailingZeroCount。

// 错：最高非零位标的是最浅层
int level = (63 - BitOperations.LeadingZeroCount(id)) / width + 1;

// 对：最低非零位落在最深层的字段里
int level = depth - (BitOperations.TrailingZeroCount(id) / width);
这类方案的通病

位段法看起来只是位运算，实际藏着一串「必须为真但没人帮你检查」的隐式约定：每层必须占槽、0 必须留空、位段方向不能搞反、容量不能超。CSR 那种结构至少会在构建期 throw。用位段码就一定要在构建期补断言，把运行时错误提前成构建失败。

06选型结论

  • 标签集合可控（四层固定、每层几百个）→ 用位段码。判父子快 8 倍、前缀深度快 5 倍、内存省 5 倍。构建期加一句 Debug.Assert(children <= 127) 就完事。
  • 只关心父子判定、不在意取链 → 用嵌套集（DFS 时间戳）。O(1) 两比较、8 B、无容量天花板，树深了不掉速。插入要重编号，所以同样是「改一次重建一次」。
  • 标签来自编辑器 / mod / DLC，运行时长度不可预测 → 才轮到 CSR 平铺。它的真实卖点是无容量上限 + 不可变快照单次 Volatile.Write 发布、读侧无锁无撕裂。这些好处跑不出来，但线上偶发的多线程 bug 跑得出来。
  • 别用字符串拼接做判定。免分配的 Span 版还能接受（8~10 ns），一旦 StartsWith(a + ".") 就翻倍。State.Stun.Hard 这种判定一次多花 20 ns，一帧做几千次就是 0.1 ms 起步。

一句话：CSR 是用 5 倍内存 + 5~8 倍的单次判定耗时，买了「这套东西永远不会因为标签变多而崩」。如果你已经知道标签规模上限，这笔钱花得挺冤。
